## Controlled local processing timing

Compared BabelDOC 0.6.4 and 0.7.1 on the same five-page Jasanoff input, with Python 3.12 and the default ONNX/CoreML layout model. Alternated old/new runs three times, serially. The completed translation job had finished before these measurements. Old-version installs constrained `bitstring<5`.

The probe loaded the model before starting the timer, disabled translation and automatic glossary extraction, and timed `async_translate` progress start/end events using `time.perf_counter`. Each process exited after the formula/style stage, before translation, typesetting, font subsetting and final PDF writing. The aggregate timer includes intervening preprocessing; the named stage measurements do not include interpreter startup or model construction. Stage boundaries are BabelDOC's reported boundaries and can include implementation-specific work, so they are useful workflow measurements rather than isolated neural-model inference benchmarks.

## Decision

The initial trial retained the existing dependency behavior pending the checks below. The follow-up adopted the pinned pair after controlled comparisons, visual spot checks and a real publication transaction; the document-specific coverage failures remain rejected.

## Follow-up validation and adoption

Compared BabelDOC 0.6.4 and 0.7.1 through the same public Python API, OpenAI translator, provider/model configuration and layout model. Disabled automatic glossary extraction in both controlled runs. Translations were not frozen across versions, so small wording and timing differences cannot be attributed solely to the engine. The old pdf2zh-next 2.9.0 wrapper could not resolve with BabelDOC 0.6.4 because their PyMuPDF requirements conflict; this is why the controlled comparison uses the public API.

| Controlled input | 0.6.4 body coverage | 0.7.1 body coverage | Alternating pages |
| --- | ---: | ---: | ---: |
| Stilgoe prepared PDF, physical pages 1–3 | 0.272771 | 0.273496 | 6 each |
| Hutchby, Media Talk (2006), physical pages 15–18 after MinerU layout OCR | 0.276477 | 0.275064 | 8 each |

All four controlled candidates remain below the unchanged 0.30 gate, with zero near-zero pages. These results and selected-page inspection do not show a material new omission from the engine upgrade, but do not prove complete translation of every page. The tested native-paper acceptance plus unchanged rejection behavior support adopting the new pair while retaining the gates.

Visual checks compared the same Stilgoe translated page (physical source page 2) in both engines, and compared the source/translation of the new scan adapter trial's weakest page (physical source-book page 17, sample page 3). The inspected paragraphs had corresponding translations, with no observed new full-paragraph omission or major overlap. Paragraph spacing remains uneven. This was a spot check, not a complete visual or semantic audit.

The scan input was a four-page slice with no old text layer. The existing MinerU command produced source-bound layout and retained recognition at `scan/recognition.json`; it reported all four pages as lacking a usable old baseline. The scan adapter run with the final pinned pair completed in 72.21 seconds, produced 8 alternating pages, and scored 0.273424. It was retained under `scan/translated/`, not published as an accepted translation.

Investigated compatibility ideographs such as `不`, `理`, and `年` in extracted Chinese. The current Han counter excludes these. Read-only NFC remeasurement of the original 13-page Stilgoe candidate raises its median from 0.272669 to 0.288981, still below 0.30. This only partly explains the low score; neither the counter nor the threshold was changed in this update. It does not establish that the original failure was entirely a false rejection.

The final adapter and configuration fingerprint were then exercised through strict `observe initial → run → observe final` on the same 5-page native input at the canonical test source role `sources/babeldoc071-native.pdf`. The transaction committed a 10-page bilingual output with coverage 0.300588, and final observation returned `signal: reused` with matching output and manifest hashes. The output is `processing/translations/babeldoc071-native-zh.pdf` in the test vault. An initial attempt using the temporary source path was rejected before provider work for `translation.source_role_invalid`; placing the sample at the declared source role resolved it.

Final validation on Mac Mini: **114 tests passed** across `test_pdf2zh_translate.py`, `test_translate_coverage.py`, `test_tounicode.py`, `test_translate_cli.py`, and `test_translation_recovery.py`. Includes the validated uvx package pair and a regression that changing the engine specification changes the backend configuration fingerprint. The complete repository suite was not run. Local `git diff --check` passed.

Production code now fixes `PDF2ZH_SPEC = "pdf2zh-next==2.10.2"` and `BABELDOC_SPEC = "BabelDOC==0.7.1"`, supplies BabelDOC via uvx `--with`, removes the bitstring workaround, and includes the engine in the existing fingerprint. This selects the engine whenever the configured backend is pdf2zh; it does not change the user's backend preference. No older user translation was overwritten.
